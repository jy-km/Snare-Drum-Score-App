## Key decisions (see `project_overview.md` for full context)

- Input method: microphone (acoustic), not MIDI input.
- Score file format: Standard MIDI File (.mid) via `dart_midi_pro`; velocity encodes accent/ghost-note dynamics.
- No anti-sharing restriction on saved files (dropped as a requirement).
- Platforms: Android/iOS only; desktop/web scaffolding to be removed from the repo.
- MVP note density: single-onset rhythm only; the "8 simultaneous notes" spec deferred to a later phase.
- ~~Rhythm entry UI: step-sequencer-style tap grid~~ — **superseded by Milestone 1.5**: real staff notation with explicit note values (1/4, 1/8, 1/16), since the tap-grid model had no concept of note duration and wouldn't generalize to pitched notes later. See Milestone 1.5 below.
- Milestone 1 includes playback of the entered rhythm (Play/Stop button, synthesized click sound, no bundled audio sample to avoid licensing questions) so users can verify entry before Milestone 2's full practice mode exists.
- Tempo is two distinct concepts: the score's stored **target tempo** (used as-is for Milestone 1's verification playback) and an independently adjustable **practice tempo** (Milestone 2 only — starts below target, increases across attempts). `rhythm_player.dart` takes tempo as a parameter so Milestone 2 can reuse it without rework.
- Milestone 2's practice screen originally played **no rhythm audio at all** — the player performs the rhythm themselves on their instrument (Milestone 4 will listen via mic). The only audio was a count-in (originally 4 beats; now `beatsPerMeasure` beats, see Milestone 3), modeled as a real "Countdown Measure" prepended to the same timeline the 8 real measures play on, so a single clock drives the whole run rather than a separate Timer racing a separate audio system. **Milestone 3 added a per-session toggle** ("Play rhythm sound") so the user can choose audible-throughout vs. count-in-only; see Milestone 3 below.

**Playback architecture was redesigned after the user tested on their own device and found real bugs** the automated checks and my own on-device checks had missed:
1. `PlayerMode.lowLatency` (SoundPool) doesn't support `BytesSource` on Android at all — threw `PlatformException(AndroidAudioError, ...)`. Fixed by using the default `PlayerMode.mediaPlayer`.
2. Default `ReleaseMode.release` tears down each player's native resources after one playthrough — since the original design reused two long-lived players (retriggered via `seek()`+`resume()`), only the *first* hit on each player could ever work.
3. Default audio focus is exclusive (`gain`) — every `resume()` call requests focus, and since playback alternated between two players (normal/accent), each stole focus from the other (confirmed via `adb shell dumpsys audio`: `requestAudioFocus()` → `event: handleLoss` → `abandonAudioFocus()` in rapid succession), cutting hits off almost immediately.
4. **User-reported, and the actual reason #1-3 weren't a full fix**: even after fixing 1-3, a single isolated accent followed by rests produced a spurious echo, and the same pattern sounded different on repeat plays. Root cause: `seek()`+`resume()` are async platform-channel round-trips; when two calls on the same player overlapped in time (plausible whenever retriggers land close together, or a stale call from a previous Play press was still resolving), `audioplayers`' `seek()` — which waits for the *next* `onSeekComplete` event — could have its wait satisfied by the wrong event, firing an extra spurious `resume()`.

**Fix: stopped retriggering clips live entirely.** `rhythm_player.dart` now renders the whole 8-measure sequence to a single linear audio buffer up front (mixing each hit's click waveform into a silent buffer at its exact sample position — the same idea as bouncing a MIDI track to audio), then plays that one buffer once via a single `AudioPlayer`. No retrigger window exists anymore, so the result is deterministic by construction; the playhead highlight is now driven by the player's actual `onPositionChanged` stream instead of a separate Dart-side stopwatch, so it can't drift from the real audio either. Re-verified via `dumpsys audio`: exactly one `MediaPlayer` created per Play press, one continuous playthrough with zero focus-request/handleLoss churn.

**Lesson** (also saved to memory for future sessions): absence of exceptions plus correct UI behavior is not proof that audio plays correctly. Bugs 1-3 were only caught by the user actually listening on real hardware; the `dumpsys audio` technique (watching for focus churn and per-player lifecycle events) turned out to be the fastest objective way to diagnose without needing to hear it myself, and should be the standard check for any future audio-playback change here.

**Two more real bugs found via user testing on the Pixel 10, both isolated to the first ~1 second of playback:**
1. **Glyph re-layout every frame.** `StaffNotationView`'s `_paintGlyph` created a brand-new `TextPainter` and called `.layout()` (font shaping) on *every* paint call. Playback's every-frame repaint (needed for smooth playhead motion) was redoing that shaping work for every note/rest/clef glyph, every frame — cost scales with how many glyphs are in the visible measure. Fixed by caching each glyph's laid-out `TextPainter` by `(glyph, fontSize)`; there are only a handful of distinct combinations in the whole app, so after the first paint ever, it's a cache hit forever. (This turned out not to be the dominant cause of the reported jank — see #2 — but is a real, worthwhile fix regardless.)
2. **The actual cause, found via temporary on-device logging** (confirmed with the user that denser-but-later measures were *not* janky, only ever the very start of playback, which ruled out #1 as the primary cause and pointed at something purely time-based): `rhythm_player.dart`'s position calibration was reacting to unreliable native position reports that only occur in roughly the first second after `play()`. Captured directly from the Pixel 10: the native player reports position as exactly `0` for ~400ms while buffering (each zero reading was dragging our calibration anchor forward, causing a visible catch-up jump once real data arrived), and separately, about a second in, one sample briefly *regressed* (637ms → 336ms — a real quirk in native reporting, not noise we introduced), which our correction dutifully followed, causing the displayed position to visibly move backward for a few frames. Fixed in `RhythmPlayer._onPositionSample`: don't calibrate off a reading below `_minStartupPosition` (20ms), and reject any sample that would move position backward (safe since we never seek during playback, so real position can only move forward). User confirmed this fixed it, with only a negligible residual flicker remaining.

**Lesson reinforced**: when a bug report includes "it's worse under condition X," verify that correlation before designing a fix around it — the user's own follow-up correction (a later, denser measure was *not* janky) is what redirected the investigation from "glyph rendering cost" to "startup-only timing issue," which turned out to be the real cause. Capturing actual on-device data (temporary logging + `flutter run`'s console output) beat further speculation.

## Milestone 2 — Practice screen

Status: **Done**, confirmed on a Pixel 10 (both the ring-buffer display logic and the count-in timing needed a real device and, for the final timing judgment, a real person tapping along in real time — screenshots and log evidence could confirm the mechanism but not the felt timing).

Scope: a new practice mode, distinct from `ScoreEditorScreen`'s verification playback. The device shows the player where they are in the score but does **not** play the rhythm's sound (Milestone 4's mic will listen instead) — an audible 4-beat count-in leads into a moving playhead across the score, with an independently adjustable practice tempo (never mutating the score's stored target tempo).

- [x] `lib/services/practice_slot_assignment.dart` (new): `PracticeSlotAssignment`, a ring-buffer tracker for 3 fixed on-screen slots (A/B/C). Slot *position* is fixed; slot *content* rotates — `slotForMeasure(idx) = idx % 3` decides both "which slot is active" and "which slot to refresh," and each refresh jumps a slot's content 2 measures ahead of the one it just finished showing, so a measure is visible for 2 full measures before it's due to be played (3 slots was chosen over 2 specifically for this margin — 2 slots would give only 1 measure of lookahead, judged too tight for denser rhythms). `measuresCount` is a constructor parameter (not hardcoded) so the practice screen could later extend the timeline (see the count-in redesign below) without changing this class's core logic.
- [x] `lib/screens/practice_screen.dart` (new): renders the 3 slots via the existing `StaffNotationView` unmodified, fades in a slot's new content via `AnimatedSwitcher` keyed on measure index, highlights the currently-playing slot, and blanks a slot instead of showing stale content once there's no measure left to refresh it with. A practice-tempo stepper is local UI state, initialized from the score's tempo but never written back to it.
- [x] `lib/screens/score_list_screen.dart`: added a `PracticeScreen` entry point per saved score.
- [x] Tests: `practice_slot_assignment_test.dart` (unit, drives the full measure-transition table including tail blanking), `practice_screen_test.dart` (widget tests for idle/tempo/count-in/playback/completion/stop) — all passing, `flutter analyze` clean.

**Two rounds of real bugs found via live testing on the Pixel 10** (screenshots + `adb shell input tap`/`screencap` to drive the app, `logcat` grepped for `MediaFocusControl`/`AudioTrack` lines to check audio-focus health — the same `dumpsys`-style technique from Milestone 1, just via `logcat` this time):

1. **3-slots-wide layout was unreadable.** The first version put all 3 measures side by side, each getting only ~1/3 of the screen width — proportional note spacing (the same formula `StaffNotationView` already used) meant notes were packed too close to read. User caught this immediately on the real device. Fixed by stacking the 3 slots full-width, one per row (like systems in sheet music), wrapped in a `SingleChildScrollView` since the stack no longer fits one screen height.

2. **Count-in clicks retriggered the same bug class Milestone 1 already fixed once.** The original count-in called `.play()` on the same `AudioPlayer` once per beat (4 calls, ~600ms apart) — back-to-back async platform-channel calls on one player race each other, exactly like `RhythmPlayer`'s old seek/resume retrigger bug. User reported "first two beats very short" or "first beat doesn't sound." First fix: pre-render all 4 clicks into one buffer, played with a single `.play()` call (mirrors `RhythmPlayer._renderSequence`'s "render once, play once" approach) — this fixed the click evenness, confirmed via `logcat` showing exactly one `requestAudioFocus`/`stop` cycle instead of four.
   - **That fix wasn't complete**: user still felt the gap between the last count-in beat and the first note of Measure 1 was shorter than a full beat. Root cause: the count-in's *visual* countdown ran on a plain Dart `Timer` starting the instant `.play()` was called, but real audio has ~hundreds of ms of startup latency before it's actually audible (the same latency `RhythmPlayer` documented and calibrated around in Milestone 1.5) — so the last click played audibly *later* than the Timer assumed, shortening the gap before playback began by exactly that latency.
   - **User's fix, implemented as-is**: instead of patching the calibration, model the count-in as a real "Countdown Measure" (4 quarter notes) prepended to the *same* timeline the 8 real measures play on, driven by one continuous `AnimationController` — not a separate Timer racing a separate audio system. The transition from the last count-in click into Measure 1 becomes ordinary continuous playhead motion across a measure boundary, identical in kind to any other measure-to-measure transition already proven smooth. The single clock is still calibrated once against the count-in click's real audio position (`AudioPlayer.onPositionChanged`, ignoring readings below 20ms exactly like `RhythmPlayer`'s `_minStartupPosition`) with a 1-second fallback in case no audio position ever arrives (e.g. no audio plugin under `flutter test`), so the fix doesn't depend on the platform channel being present to stay testable. `PracticeSlotAssignment.measuresCount` (see above) is what let this become a 9-measure timeline (count-in + 8 real measures) without changing the ring-buffer math itself.

**Lesson reinforced**: the same retrigger-bug shape (repeated `.play()` calls on a shared player) showed up a second time in a new context — worth treating "don't retrigger a shared audio player, render once and play once" as a standing rule for this codebase rather than something to rediscover per-feature. Separately, a bug fix that addresses the reported symptom (uneven clicks) isn't necessarily the *whole* bug (the timing-gap issue was a distinct root cause underneath) — the user's own architectural suggestion (unify the clock instead of patching the calibration) turned out to be a better fix than the calibration patch already in progress.

All 26 tests passing, `flutter analyze` clean.

**Bug found while wiring the real samples in**: making sample loading async but keeping `PracticeScreen._start()` `async` and `await`ing the render before scheduling `_countInFallbackTimer` broke the practice-screen tests -- the fallback timer (which exists specifically to start the timeline when no real audio position ever arrives, e.g. under `flutter test`'s fake audio channel) never got scheduled within the test's fake-time `pump()` window, because it was now gated behind a real (if normally fast) asset-read. Fixed by keeping `_start()` synchronous and moving the `await`ed render+play into a separate fire-and-forget (`unawaited`) helper, so the fallback timer's scheduling is unconditional again, matching the original design intent from Milestone 2 (the fallback exists for exactly this "audio subsystem is unavailable/slow" case, so it must not itself depend on the audio subsystem being fast).

**Not yet flagged to the user, worth checking on-device**: `snare.wav`'s recording is ~3.3s long (588KB stereo 16-bit at 44.1kHz) versus kick's ~0.35s and tambourine's ~0.59s -- at faster tempos or dense sixteenth-note passages, overlapping snare tails will sum in the mix buffer (clamped to int16 range, so no crash, but potentially washy/distorted-sounding). Not addressed -- the user may want to trim that file.

**Real device bug, user-reported: pressing Play did nothing at all** (no sound, no moving playhead, no button-state change). Root cause: `main()` fired `unawaited(ClickSound.preload())` *before* `runApp()`, but `preload()`'s `rootBundle.load()` calls need the widgets binding initialized first -- `runApp()` does that, but only once it starts, which is after the fire-and-forget preload call had already begun running. On a real device this made the very first asset load throw immediately; because `ClickSound._samplesFor` cached the *Future itself* via `putIfAbsent`, that one early failure got cached forever, so every later `RhythmPlayer.play()` call replayed the same cached rejected Future and failed identically for the rest of the app's life -- explaining why it failed every single time, not just on first launch. Since nothing awaited or caught that rejection anywhere in the call chain (`_togglePlay` → `RhythmPlayer.play` → `ClickSound.normalSamples`/`accentSamples`), the failure was completely silent: `_isPlaying` never flipped, so the Play/Stop icon, the position stream, and the moving playhead all simply never started.

Fixed three ways: (1) `main()` now calls `WidgetsFlutterBinding.ensureInitialized()` before the preload call; (2) `ClickSound._samplesFor` now evicts a failed load from its cache on error instead of caching the rejection forever, so even an unrelated future failure self-heals on the next attempt rather than permanently bricking playback; (3) `score_editor_screen.dart`'s `_togglePlay` now wraps `_player.play()` in try/catch and shows a SnackBar on failure (and force-updates the button immediately on success, rather than waiting on the first real audio-position sample), and `practice_screen.dart`'s `_playCountIn` now catches and `debugPrint`s a failure from the render step too (previously only the native `.play()` call itself was guarded, not the sample-loading `await` before it) -- so a future failure is visible instead of indistinguishable from "the button doesn't work."

**Lesson**: a `Future`-valued cache (`Map<K, Future<V>>` via `putIfAbsent`) caches failure just as durably as success -- a transient or ordering-dependent error on the very first call can look like a permanent, unexplainable bug ("it never works") rather than the one-time fluke it actually was. Any such cache needs an eviction path for the failure case, not just the success path. Separately: async code on a fire-and-forget path (`unawaited(...)`) is exactly where silent failures hide, since nothing forces the error to surface -- worth grepping for `unawaited` and unguarded `await` chains whenever a "the button does literally nothing" report comes in.

**Lesson**: when a fix touches multiple call sites that all derive from the same now-stale assumption (here, "measure capacity is always 4/4"), grep for every call site before declaring the fix done -- `_appendEvent`'s capacity check was updated but the three duration buttons' own independent `canAppend` checks in `build()` were missed, and only surfaced because the user tried it on a real 5/4 and 6/4 score.

## Growable measure count (beyond Milestone 3)

Status: **Done**, confirmed working on a real device by the user.

Scope: the score used to be rigidly fixed at 8 measures (`RhythmGrid.measuresCount`, asserted in `RhythmScore`'s constructor, hardcoded into the MIDI codec's decode loop and the editor's measure-tab strip). The user asked to make it start at 8 but be growable via a "+" button, with the growing set of measures reachable by swiping rather than the tab strip staying a fixed-width row.

- [x] `lib/models/rhythm_score.dart`: `RhythmGrid.measuresCount` renamed to `RhythmGrid.defaultMeasuresCount` (now just the starting count for a new score, not a hard limit); `RhythmScore`'s constructor assert relaxed to `measures.isNotEmpty` instead of `== 8`; `RhythmScore.empty()` takes an optional `measuresCount` parameter; added `RhythmScore.appendMeasure()` (mirrors `copyWithMeasure`) that returns a copy with one new empty `Measure` appended.
- [x] `lib/services/midi_score_codec.dart`: decode no longer hardcodes 8 measures. `encode` already wrote `EndOfTrackEvent` at exactly `measures.length * unitsPerMeasure * ticksPerSixteenth`; decode now recovers the measure count from that same tick (`absoluteTick` at the end of the event-processing loop, since `EndOfTrackEvent` is always the last event) instead of a fixed constant -- so a grown score's full length survives a save/reload round-trip with no new meta-event needed. Old files saved before this change still decode correctly (their end tick was always `8 * measureLengthTicks`, so they recover as exactly 8 measures).
- [x] `lib/screens/score_editor_screen.dart`: the measure-tab strip (`_MeasureTabStrip`) was rewritten from a `Row` of `Expanded` buttons (which just squeezed every button narrower as more were added -- unworkable once the count is unbounded) to a horizontally scrollable `ListView` of fixed-size (40x40) circular buttons (`_MeasureTabButton`, `shape: CircleBorder()`), swipeable left/right. A same-sized circular "+" button (`Key('measure_tab_add')`) sits at the end; tapping it calls `_addMeasure()`, which appends an empty measure and immediately jumps `_activeMeasure` to it. The strip auto-scrolls itself to the end (`ScrollController.animateTo` in `didUpdateWidget`, detecting `measureCount` increasing) whenever a measure is added, so the new tab and "+" button are visible without the user having to swipe manually. `_MeasureTabStrip` had to become a `StatefulWidget` (previously stateless) to own that `ScrollController`. Existing `Key('measure_tab_<index>')` keys are preserved.
- [x] `lib/screens/practice_screen.dart`: `_timelineMeasureCount` (previously a compile-time `static const` built from the old fixed constant) is now an instance getter (`widget.score.measures.length + 1`), and `_slots` changed from `final` to `late final` accordingly (a `late final` field initializer can reference `widget`/instance getters; a plain `final` field initializer cannot, since it runs before the state object's `widget` is attached).
- [x] `lib/services/practice_slot_assignment.dart`: default constructor parameter renamed to match (`RhythmGrid.defaultMeasuresCount`); behavior unchanged, since `practice_screen.dart` always passes an explicit `measuresCount` anyway.
- [x] Tests: `midi_score_codec_test.dart` -- a score grown to 11 measures (8 default + 3 appended) round-trips its full length and the last measure's content; `widget_test.dart` -- tapping the "+" button appends measure 9, jumps to it (confirmed empty), and leaves measure 1's content untouched. All 28 tests passing, `flutter analyze` clean.

**Not done**: no upper bound on measure count (the user didn't ask for one, and none of the surrounding code needed one for correctness, so none was added) -- a user could in principle add an impractically large number of measures with no warning. Also not addressed: removing/shrinking measures (only appending is supported, consistent with the append-only philosophy `Measure` itself already uses for note entry).

## Milestone 3.5 — Half-note-beat meters (1/2-8/2)

Status: **Done**. Not yet verified on a real device.

Scope: Milestone 3 only ever supported a quarter-note beat (the X/4 family, 1/4-16/4). The user asked to add the X/2 family (1/2-8/2, a half-note beat) as additional selectable meters in the same "Meter" button -- not a replacement.

- [x] `lib/models/rhythm_score.dart`: `RhythmScore` gained a `beatUnit` field (4 or 2 -- `RhythmGrid.beatUnits`), defaulting to 4 (every prior score/test is unaffected). `unitsPerMeasure` generalized from `beatsPerMeasure * subdivisionsPerBeat` (which silently assumed a quarter-note beat) to `beatsPerMeasure * (RhythmGrid.unitsPerWholeNote ~/ beatUnit)` -- a half-note beat is 8 sixteenth-note units (`16/2`) instead of a quarter note's 4 (`16/4`). The numerator's valid range depends on the denominator (`RhythmGrid.maxBeatsPerMeasureFor(beatUnit)`: 16 for a quarter-note beat, 8 for a half-note beat, both asked for literally), so the constructor assert and the `_MeterButton` popup's per-group range both call that instead of a single fixed max. Threaded through `copyWith`/equality/hashCode like every other meter-related field.
- [x] `lib/services/midi_score_codec.dart`: the MIDI time-signature meta-event already has a real denominator field (`dart_midi_pro`'s `TimeSignatureEvent.denominator`, confirmed by reading the package source directly -- it stores/reads the literal denominator value, e.g. 2 or 4, handling the MIDI spec's power-of-2 exponent encoding internally) that was previously always written as `4` and never read back on decode. Encode now writes `score.beatUnit`; decode now reads it (defaulting to 4 if absent, e.g. for files saved before this change) and uses it for the measure-length math instead of assuming a quarter-note beat.
- [x] `lib/screens/score_editor_screen.dart`: the "Meter" popup (`_MeterButton`) now lists both families in one scrollable list -- 1/4..16/4, a `PopupMenuDivider`, then 1/2..8/2 -- selected via a `(int, int)` record `(beatsPerMeasure, beatUnit)` instead of a bare int. **Key names changed** from `meter_option_<n>` to `meter_option_<n>_<unit>` (e.g. `meter_option_7_4`), since the two families overlap on numerator values (1-8 exist in both) and would otherwise collide; the existing widget test using the old key name was updated. Button label is now `Meter: $beatsPerMeasure/$beatUnit` instead of a hardcoded `/4`.
- [x] **Bug found and fixed while implementing, before the user could hit it**: `lib/screens/practice_screen.dart`'s count-in spaced its audible clicks using the hardcoded constant `RhythmGrid.subdivisionsPerBeat` (4 units/beat) regardless of the score's actual beat unit -- correct for a quarter-note beat, but exactly half the correct length for a half-note beat (8 units/beat), which would have made the count-in finish early and thrown off the single-clock-calibrated timeline's sync with the real measures (the same invariant Milestone 2 was built around). Fixed via a new `_unitsPerBeat` getter (`unitsPerMeasure ~/ beatsPerMeasure`) used both for the audible click spacing and (since there's no "half note" `NoteValue` to notate it properly) for sizing the count-in's visual placeholder measure as 2 quarter notes per beat instead of 1 when the beat unit is 2, so the displayed count-in measure's total width still matches a real measure's.
- [x] Tests: `midi_score_codec_test.dart` -- a 3/2 score round-trips its meter and note content; `widget_test.dart` -- selecting 3/2 updates the label and measure capacity (24 units), and confirms 8/2 exists but 9/2 doesn't in the same popup as 16/4 (had to scroll the now-25-item popup into view with `ensureVisible`, the same technique `practice_screen_test.dart` already used for its off-screen action button); `practice_screen_test.dart` -- a 3/2 score's count-in takes the full correct 6s (3 beats × 8 units × 250ms at 60 BPM) rather than the buggy 3s, confirmed by checking the status text is still "Get ready..." at 5.5s and "Playing" by 6.2s. All 31 tests passing, `flutter analyze` clean.

**Not done**: denominators other than 2 and 4 (e.g. 6/8, 3/8) remain unaddressed -- `RhythmGrid.unitsPerWholeNote` and `beatUnits` only cover the two the user asked for; see Open questions.

### Eighth-note triplets (added to Milestone 3.5)

Status: **Done**. Not yet verified on a real device -- in particular nobody has *listened* to a triplet yet (see Milestone 1's lesson: passing tests are not evidence audio sounds right).

Scope: the user asked for eighth-note triplets, entered the same way as 1/4, 1/8 and 1/16 (one button press appends one note), with the button labeled "Triplet", and for the note buttons to scroll horizontally when they don't fit the screen.

- [x] **Grid resolution changed, app-wide.** A triplet eighth is 1⅓ sixteenth notes, so it can't be an integer on the old sixteenth-note grid. The unit is now 1/12 of a quarter note (`RhythmGrid.unitsPerQuarterNote = 12`, replacing `subdivisionsPerBeat = 4`): quarter = 12, eighth = 6, triplet eighth = 4, sixteenth = 3 units; a 4/4 measure is 48 units instead of 16. `NoteValue.sixteenthUnits` was renamed `NoteValue.units` since the unit is no longer a sixteenth. Everything downstream (`unitsPerMeasure`, the playhead position, `StaffNotationView`'s x-positions, the practice timeline) already worked in "units" and needed only the constant swapped. **User-visible side effect**: the editor's "N/M units filled" line now counts in the new units (a quarter note reads "12/48", not "4/16").
- [x] `lib/models/rhythm_score.dart`: `NoteValue.eighthTriplet`. No grouping is enforced -- a triplet note is just a 4-unit event, so an incomplete group (1 or 2 triplets followed by something else) is allowed, the same append-anything-that-fits philosophy as the other values. A measure can therefore end up with 1, 2 or 5 units left that no note value fills; the user has to backspace out of that.
- [x] `lib/services/midi_score_codec.dart`: 40 ticks per unit (480/12), so a triplet eighth is the standard 160 ticks and files saved before this change decode unchanged (their durations are the same tick counts as before). The rest-filling for silent gaps had to change from a plain greedy pass to a backtracking one (`_restsForGap`/`_fitRests`): the gap before the last note of a triplet group is 8 units, and greedily taking an eighth rest (6) strands 2 units nothing fills. Mid-triplet positions prefer triplet rests so a lone triplet note decodes as "note, triplet rest, triplet rest, then quarter rests" rather than with the triplet rests pushed to the end.
- [x] `lib/widgets/staff_notation_view.dart`: a triplet eighth is drawn with the ordinary eighth note/rest glyph plus a "3" (SMuFL `tuplet3`, U+E883) above -- with a bracket spanning the group for every 3 (or trailing 2) consecutive triplet events, and a bare "3" over a lone one. Checked by rendering a measure to a PNG with the real Bravura font under `flutter test` (temporary test, not kept).
- [x] `lib/services/rhythm_player.dart` + `lib/screens/practice_screen.dart`: both audio renderers used to round samples-per-unit to a whole number once and multiply by the unit position. With units 3x smaller that rounding error would accumulate 3x faster (up to ~4ms over 8 measures) against the playhead, which uses the exact value -- so both now keep samples-per-unit fractional and round each hit's position individually.
- [x] `lib/screens/score_editor_screen.dart`: "Triplet" button (`Key('duration_eighth_triplet')`) after 1/16. The button row is now `_NoteEntryStrip` (`Key('note_entry_strip')`): centered when it fits, horizontally swipeable when it doesn't (five buttons no longer fit a ~360dp-wide phone).
- [x] Tests: `midi_score_codec_test.dart` -- a measure mixing full triplets, triplet rests on either side of a note, and eighths round-trips exactly; a lone triplet note decodes with its group and measure completed by rests. `widget_test.dart` -- three triplets fill exactly one quarter note, capacity checks hold with triplets (4 units left takes a triplet but not an eighth), and on a narrow screen the strip scrolls to reach the backspace button without a layout overflow. Existing tests' unit counts updated for the new grid. All 35 tests passing, `flutter analyze` clean.

**Noticed, not changed**: in that narrow-screen test the tempo/meter row and the Rest/Normal/Accent row overflow at phone-like widths (≤ ~400px). The test font is far wider than the real one, so this is probably a test artifact rather than a real-device problem (the user has been using those rows on a Pixel 10), but they have no scroll fallback if a narrower phone ever does run out of room.
